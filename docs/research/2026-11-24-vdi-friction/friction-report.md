## 结论

**10 条**：P1 两条、P2 五条、P3 三条。另外，这次审计**抓到了交付物本身的一处实错**（N4）——它当初被流程放过了，正是本次要回答的问题。

一句话概括：这套流程的强项是**逼你写出会失败的测试**（S1 破坏变体、S3 先红后绿），弱项是**把登记表当收口**——S5 唯一的机器门只验格式，不验证据；而它自己声称的「人眼核对不算核对」（SKILL.md:75）比这道门能做到的强。

## N1 截断静默通过（P1）

`readTable` 遇到第一个不以 `|` 开头的行就 `break`（`check-register.mjs:50-55`）。表格中间插一个空行，后面的行全部不解析，而 `rows` 计数只用来判断「是不是一行都没有」（`:207`）——**读了一半不等于读了**。

复跑 E2 实测：19 行的表插一个空行 → `rows=9 / verdict=OK / exit=0 / errors=[]`。

这跟技能自己第四轮试点修过的是同一种病（`pilot-findings.md:46-51`：输入集为空必然通过 → 候选数为 0 就 exit 2）。**空集修了，截断没修**。上一次运行里这条就真的发生过一次（9/19 仍报 OK），是我自查时偶然发现的，不是核对器报出来的。

修法：`break` 之前记下位置，循环结束后继续扫剩余行；只要还有 `|` 开头的行就 ERROR。验收：把复跑 E2 的期望从「OK」改成「FAIL」，脚本仍 exit 0。

## N2 S5 的机器门只验格式（P1）

技能把 `check-register.mjs` 的 `exit 0` 写成 S5 的出口判据（`SKILL.md:31,75`；`stations.md:108`），但：

- 这个脚本只在 `--strict` 下把 WARN 计失败（`:216`），而文档给的命令**不带** `--strict`；
- 它从不执行任何命令，「退出码」列只是文本匹配 `0` 或 `PASS`（`:120-127`）。

复跑实测：

- E3：把 P19 的证据路径改成 `does-not-exist.sh` → `verdict=OK exit=0`，只有 1 条 WARN；
- E4：同一份文件加 `--strict` → `exit=1`（修法是现成的，只差默认值）；
- E5：破坏变体列写 `bash tests/never-ran-this.sh`、退出码照抄 `0` → 仍然 `OK`。

所以「登记表机器核对 exit 0」能证明的是**表读得进来、字段没写错**，不能证明**证据跑过**。脚本头部（`:10-11`）其实老实说了这一点，是**文档把它抬得比它能做到的高**。这不是要废掉这道门，是要把 S5 的出口判据写回它能兑现的那句：「表能被下一个人读、格式无错；证据是否跑过由 S1/S3 的红绿负责」。

## N3 S1 的人确认门没有收据（P2）

`SKILL.md:27` 与 `stations.md:22` 都要求「先画图让人确认转移对不对，再写 PlusCal → TLA+」。但：

- 登记表列里没有「图/确认」这一项（`property-register.md:7`）；
- 验证记录 A 分区只收「性质原文 / 破坏变体文件 / 报红输出 / 退出码 / -workers」（`verification-record.md:22-26`）。

于是这一步**只能靠自觉**：做过没做过、谁确认的、确认的是哪一版图，事后全查不到。本次运行的模型与两张图在同一个提交里（`2f49ffd`，复跑 E7），提交里没有任何确认记录——能证明「没记录」，不能证明「没做」。这类门要么给收据位，要么就别写成出口判据。

## N4 交付的图说错话（P2）

这条是审计改出来的实错，不是流程建议：

`chart-fixed.mmd` 的边是 fixed 顺序（config → target → collector），但状态名沿用了 current 那份：

```
s1 --> s2: the config files land
s2: visible source after 1/3 files      ← 错：此刻采集器还没落盘，源不可见
s2 --> s4: the target file lands
s4: visible source after 2/3 files      ← 错：同理
```

`Order.tla:4` 写明「采集器一出现在盘上，插件下一轮就当数据源」，`:8-10` 写明 fixed 是 `3 → 2 → 1`。所以 s2/s4 的标签与模型语义直接冲突。**这是本次运行里唯一一处「门都过了、内容却错」的地方**，恰好落在 N3 那个没有守门的站上：图是手写的，没有脚本把图和模型对表。

修法：状态按「采集器在不在」命名（如 `configs on disk, source invisible`），或干脆从模型自动生成；再加一条对表检查（状态数、边的源/汇、每步的可见性断言）。

## N5 S0 要 sync commit，时点对不上（P2）

`SKILL.md:26` 的 S0 出口要求「每条性质一句话、一个 owner、覆盖的文件/函数、**sync commit**」；`stations.md:14` 同。但模板把 sync commit 定义为「模型与代码对齐时的 commit」（`property-register.md:22`）——S0 还没写代码，这个 commit 不存在。

结果是这一列在 S0 阶段无可核语义：写历史 commit 不是它，写 pending 又违反出口判据，只能事后回填。本次登记的 P1–P9 写 `0e5e1ac`，那是对齐前的旧提交，读者无法判断它是不是「对齐时」的那个。

修法：S0 只要「基线 commit」（验的是从哪个版本开始）；「sync commit」在 S5 才要求，未跑就 `pending`。

## N6 等级轴被旁路（P2）

`property-register.md:17` 用 S1–S4 定义 `L1/L2/L3`；`:21` 又让「不建模」写进**同一列**。核对器只有一条规则吃这一列：出现字面 `L3` 就必须有 S4 的 `PASS`（`check-register.mjs:111-118`）。

于是实际登记表里：18 行写「不建模（理由，由谁覆盖）」，唯一建模的 P19 写「**TLA+/TLC 建模**」——两个都不是 `L1/L2/L3`，等级规则**一行都没触发**。P19 事实上是 L2（模型 + 崩溃重放 + 守门测试），但读者看不出来。

修法：`不建模` 单独成列（或单独一张「不建模清单」表，写明谁覆盖）；等级列只允许 `L1/L2/L3`，不允许自由文本。

## N7 文档规则没有守门（P2）

`toolchain.md:72` 写得很清楚：`out/`、`states/`、`<模块>_TTrace_*` 都别进版本库。本次提交 `2f49ffd` 带进了 **26 个 `states/*.st` + 4 个 `_TTrace_*`**（复跑 E7），至今仍在跟踪。

这不是「忘了」那么简单：这是**一条只写在文档里的规则**，没有任何 lint、`.gitignore`、CI 检查拦住它，而技能自己第 66 行说「新增规则必须能指到一次具体事故」「同一条提醒写第二遍就编码成结构」。这条规则已经写了，但没编码。

修法：`.gitignore` 加三行 + 一条 lint（扫 `docs/**/states/` 与 `*_TTrace_*` 是否被跟踪）。注意 TTrace 是否要留作反例证据：如果留，就把它们移到明确的 `evidence/` 下并在 toolchain 里改口径，别一边说别入库一边又靠它们当证据。

## N8 改名残留（P3）

`SKILL.md:31` 仍写「见下『可重跑的四项要求』」，而正文章节已改名「六条判据」（`:33`）；`verification-record.md:42` 还叫「可重跑四项」；`pilot-findings.md` 三处引用「S5 四项」。复跑 E6：旧称 3 次、标题 0 个、`check-paths` 仍 exit 0——因为那个检查器只核对**反引号里的路径**，不核对引号里的小标题。

后果不是排版问题：⑤「证据命令落成仓库脚本」与⑥「观察值不算证据」是后来加的，旧称会让人以为只有四项、漏掉后两条。

修法：统一成「六条」；`check-paths` 增一条「引号内若像标题，检查技能内是否存在同名标题」。

## N9 S3 第三条门只对函数成立（P3）

`stations.md:73` 与 `verification-record.md:31` 把第三条门写成一个具体改法：「把被测函数体换成 `return undefined` 重跑，这条测试必须仍然失败」。这对函数有效，但本次 19 条性质里大部分的被测对象不是函数：生成的 shell 采集器、target 判定脚本、bundle 接线形状、i18n 词典完整性、jsx 渲染树。

P10–P18 的破坏变体都是「改生成器 / 改接线 / 删一条词典」，没有一条声明做过「桩掉被测逻辑仍须红」的检查（登记表破坏变体列）。不是我偷懒，是门写成了**一个动作**而不是**一类判据**，换产物类型就得自己重推。

修法：改写成类判据——「把被测单元换成失效实现（返回空 / 写空文件 / 不注册 / 不翻译），这条测试必须仍红」，并给 2 个非函数例子。

## N10 toolchain 只记「会崩」不记「坏样」（P3）

`toolchain.md:69` 记了 statechart 遇 `Seq` 会崩（附二分实测）。但 **Mermaid 标签里的非 ASCII 会被转成数字实体**（`&#65288;` 之类）这条没有任何记录（复跑 E8：13 份 md，0 份提到）。本次是**看到渲染出来的图**才发现的，于是全部标签改成英文。

「会崩」和「不崩但坏样」是两种失效：前者有报错、有人会去查；后者只是难看，容易被当成没问题交付出去。

修法：在 toolchain 的四条硬约束里加第五条，一句话 + 一个例子即可。

## 守住的部分（不只报坏消息）

1. **「每条性质一个破坏变体、亲眼见它红」真的抓到了东西。** 登记表 P8 的破坏变体列写着三条反证，其中一条是把 `label` 改回引用组件内变量 → `tr is not defined`——静态检查与纯函数测试都看不见，只有真渲染冒烟能看见。这条门是这套流程最值钱的部分。
2. **「观察值不算证据」挡掉了一个会过期的承诺。** 报告里状态数只写成「10 状态 / 18 步（TLC 实测，`-workers auto`）」，没有挂进 `守住`；登记表的 `守住` 行也没有步数。
3. **S0 的筛选在起作用。** 19 条性质里只建模 1 条（P19），其余 18 条明确写「不建模 + 谁覆盖」。这不是偷懒，是 S0 判据（坏了最贵 × 测试最摸不到）把成本压在了该压的地方。

## 观察，不算缺陷

- **S4 在这条功能上没有可达面。** 登记表 S4 列 19 行：10「未做」、5「部分」、4「—」，0 行 PASS。这个功能没有生产日志面，`-workers` 之外能做的只有测试与模型。模板已写明「S4 未过的行最高记 L2」，所以这是**口径正确**，不是摩擦；但如果下一个人读到「五站全过」，会误解。
- `research-nex` 的 validator 这次仍打印 `network_unavailable=True`（上一轮已报过的硬编码常量）。本运行**完全没用网络**，所以这个字段在这里连「降级理由」都不成立，只是噪音。

## 未判定 / 不在本报告结论里

- 「先画图让人确认」是否真的发生在建模之前——提交历史无法区分，两个模板都没有这个字段（`open_gaps` 第 1 条）。
- 本次**没有**重跑登记表 19 行声称的命令。那是 add-source 的功能回归，不属于流程摩擦审计；所以「那些 0 仍然成立」不在本报告结论里。
